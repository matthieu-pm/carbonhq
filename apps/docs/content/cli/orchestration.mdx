Orchestration is one agent starting other sessions with `carbon`. You ask the agent in one session to "work through these four issues", and it starts four sessions, one per issue, each with its own worktree and branch. You watch them in the conversation's Crew section.

Use it for work that is truly separate: separate branches, separate pull requests. Steps of one task belong in one session.

## Before you start

Install `carbon` and its skill. See [Install](/cli#install). The skill tells Claude Code, Codex and pi when and how to use `carbon`, so you can ask in plain words. You do not type the commands yourself.

## Fan work out

Ask in the conversation, for example:

> Start a session for each of DRA-51, DRA-52 and DRA-53.

The agent runs `carbon session new` once per piece of work. Each new session:

- gets its own worktree, starting at `origin/<default branch>`
- inherits the caller's agent, model, effort, fast mode and permission mode, unless the agent passes flags
- starts working at once, on the prompt the agent wrote for it

The new session has none of the calling conversation. A good prompt carries the issue text, the steps to reproduce and the constraints. See [Sessions](/cli/sessions#start-a-session) for every flag.

## Where spawned sessions show

**In the sidebar**, each new row appears under the session that started it. The app does not switch to it, so you stay in the conversation you were in. A session started by a spawned one nests a level deeper.

**In Crew**, inside the conversation's pinned summary. Running sessions and sessions waiting for you appear first. Finished sessions sit under the **done** count; click it to expand the list. Click a session row to open its full conversation. Permission and question cards show under its row, so you can answer them without leaving the parent conversation.

⌘⇧C shows or hides Crew. You can also toggle **Crew** in **Summary options**. Showing Crew opens the summary if it was closed. In a narrow window, the summary opens as a popover. You can change the shortcut in Settings → Shortcuts.

### Hidden sessions

A session started with `--hidden` shows in the crew only, not the sidebar. The skill has agents hide review sessions by default. To move one into the sidebar, right-click its crew row and choose **Show in sidebar**.

## Review with a second model

`--base` starts a session's worktree from existing work. Point it at a session id and the new session gets its own checkout of that session's branch:

```bash
carbon session new --hidden --harness codex --base <session-id> \
  "Review the work on this branch. Send your findings back to <session-id> with carbon session send."
```

Ask for this in plain words: "have Codex review this". The reviewer reads the same commits in its own worktree, so it collides with nobody.

- **Committed work only.** Changes not yet committed are not in the reviewer's tree. Commit first, or the review misses them.
- **A new branch.** The reviewer works on its own `worktree-<name>` branch. It never checks out yours, so it cannot commit onto your work.
- `carbon` prints what the id resolved to: `Started "…" in worktree calm-owl, based on worktree-brisk-jade`.

`--base` also takes a branch, tag or commit.

## Messages between sessions

```bash
carbon session send <session-id> "Review done: two findings, both fixed on worktree-calm-owl."
```

Any session can message any other. A child reports back to its parent, or a parent hands a child more context. The message starts a turn in the receiving session, or waits for the current turn to end. The receiver is told which session sent it and its id, so it can reply.

Each message costs the receiver a whole turn, so agents should send one when the other session needs it, not to say "done".

## Check on sessions

```bash
carbon session ls
```

Lists the project's sessions with their status. Nothing reports back on its own. If you want to know when sessions finish, watch the sidebar and the crew, or ask the children to send a summary when they are done.

## Work across machines

Use `carbon --machine <name> session new` to start work on another connected machine. Model and permission settings still inherit from the caller, but the worktree uses the other machine's checkout. Messages can return only if that machine also has a connection back to this one. See [Work on another machine](/cli/servers#work-on-another-machine).

## Permission prompts

A spawned session inherits the permission mode of the session that started it, and `carbon session new` has no flag to change it. If the calling session asks before it edits files or runs commands, so does every session it starts. Each one stops at its first permission card and waits for you.

Answer those cards in the crew, or open the session. To have children run without stopping, change the permission mode of the parent before it fans out.

`carbon` itself never raises a permission card in a Claude Code session.

## Limits

- **Two levels deep.** A spawned session may start sessions; those may not. Start the next batch from a top-level session.
- **No reading transcripts.** A session can create, list and message others, but cannot read what another session wrote. Ask it to send a summary.
- **No shared checkout.** Every spawned session gets its own worktree. Two sessions cannot run in one directory.
- **No permission flag.** Children always take the parent's permission mode.
- **The crew lists direct children.** A grandchild shows in its own parent's crew, not the top one.
