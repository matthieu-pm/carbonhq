Two command groups, for two sides of the same setup:

- `carbon server` runs on the machine that will **be** a server: a Linux box, or a Mac with no Carbon app. It installs what is missing and keeps the server running.
- `carbon machine` manages the machines **this server can reach**. On a Mac with the app, it is the same list as Settings → Servers. It also works on a headless server.

For the full walkthrough of putting Carbon on a Linux server, see [Connect a server](/server).

## carbon server

```bash
carbon server install
carbon server status
```

| Command | What it does |
|---|---|
| `install` | Installs what this machine is missing, then starts the server in the background. |
| `start` | Runs the server in the background, surviving logout and reboot. |
| `run [args]` | Runs the server in this terminal instead. |
| `stop` | Stops the server and removes it from the background. |
| `status` | Says whether the server is running, and its public address if it has one. |
| `tunnel on` / `tunnel off` | Puts a public address in front of the server, or takes it down. |
| `pair` | Prints a QR code for adding this server to the Carbon iPhone app. Needs a public address first. |

### Install

```bash
carbon server install
carbon server install --tools git,gh,claude_code
```

Lists what is already here, asks what to install from what is missing, then starts the server. The choices are git, the GitHub CLI and the five agents (`claude_code`, `codex`, `pi`, `fx`, `grok`). On Linux it also offers **Browser for agents**, the system libraries `carbon browser` needs, and **ffmpeg**, which `carbon browser record` needs. Those two install with apt only.

`--tools` installs the ones you name without asking. With no terminal to ask in and no `--tools`, it installs nothing and says what is missing. Anything that needs admin rights it cannot get is printed for you to run yourself.

It then lists the agent logins still to do, and ends by printing the SSH line to paste into the app's **Add server**.

A first install from `install.sh` runs this for you on any machine without the Carbon app.

### Start, run, stop

```bash
carbon server start
carbon server run --port 7317
carbon server stop
```

On Linux, `start` installs a systemd user service, `carbon.service`. If your user has no linger, the server stops when you log out, and `start` prints `sudo loginctl enable-linger <user>` to fix that. Read its log with `journalctl --user -u carbon`. With no systemd user session at all, `start` refuses; run `carbon server run` under tmux or nohup instead.

On a Mac with no Carbon app, `start` installs a login agent. Its log is `~/.carbon/server.log`. It runs only while your user is logged in, so a headless Mac wants automatic login. For the app on another Mac to reach it, turn on Remote Login in System Settings → General → Sharing.

`run` passes what follows to the server. Its one option is `--port`: the port it listens on, 7317 by default, or `0` to pick a free one.

`start` never restarts a server that is already running, since that stops its agents. After `carbon update`, it prints the command that restarts it onto the new version.

`stop` stops the background server and removes the service. It removes only the server `carbon server start` installed.

### Public address

```bash
carbon server tunnel on
```

Gives the server a public address that stays the same across restarts, and waits for it, up to two minutes. In a terminal it prints the address and a line to paste into the app: Settings → Servers → Add server → Use an address and token. Anyone holding that line can use the server.

`carbon server tunnel off` takes the address down. The server is then reachable over SSH alone. The address is off until you turn it on.

### Pair an iPhone

```bash
carbon server pair
```

Prints a QR code for the server's existing public address. Scan it with the iPhone's Camera or Carbon's **Add server** scanner. If the server has no public address yet, run `carbon server tunnel on` first. Anyone holding the QR code can use the server.

### On a Mac with the Carbon app

The app runs this Mac's server, so `start`, `run` and `status` are refused with `the Carbon app runs this Mac's server`. `install` still installs tools and then stops. `tunnel on` and `tunnel off` work, and do the same as the Remote access switch in Settings → Servers.

To run a second server beside the app anyway, give it its own data directory with `CARBON_HOME`.

### Older spellings

These still work, because the app runs them on servers with older CLIs:

| Older | Now |
|---|---|
| `carbon setup` (`--install <tools>`) | `carbon server install` (`--tools`) |
| `carbon serve` | `carbon server run` |
| `carbon service start` / `status` / `uninstall` / `tunnel on\|off` | `carbon server start` / `status` / `stop` / `tunnel on\|off` |

## carbon machine

```bash
carbon machine add vps root@203.0.113.7
carbon machine ls
```

Edits this server's machine list. On a Mac with the app, changes show in Settings → Servers. On a headless machine, the list belongs to its background server and works with no window open.

| Command | What it does |
|---|---|
| `add <name> <address>` | Adds a server. It connects first, and is saved only if that works. |
| `ls` | Lists the servers: name, address, and `connected`, `connecting`, `disconnected` or `off`, with the last error if it failed. `--json` for scripts. |
| `rename <name> <new-name>` | Renames a server. An empty name, `""`, puts back its host. |
| `connect <name>` | Connects now, or tries again on one that failed. Waits and says how it went. |
| `disconnect <name>` | Stops connecting. It stays on the list with its token, and its agents keep running. |
| `rm <name>` | Takes a server off the list, with its token. Its agents keep running there. |

Each name belongs to one server; `add` and `rename` refuse a name another server has.

### Add a server

The address is an SSH login, or a `ws://` or `wss://` address. Use a Mac's **Remote access** address and token to reach its app-managed server:

```bash
carbon machine add vps root@203.0.113.7
carbon machine add vps ssh -p 2222 root@203.0.113.7
carbon machine add vps my-ssh-alias
cat serve-token | carbon machine add vps ws://127.0.0.1:7317
carbon machine add --token-file serve-token vps ws://127.0.0.1:7317
carbon machine add --token-file serve-token mac wss://example.opentunnel.xyz
```

For SSH, everything after the name is the login, so it needs no quotes. Carbon uses this machine's own `ssh` and reads the server's token over that login. A login can take most of a minute. The host key and your login key must already be trusted; `add` does not approve a host or answer a password prompt for you.

A `ws://` or `wss://` address needs the server's token, from `~/.carbon/serve-token` on the server or its Remote access settings. Pass it with `--token-file`, which must come before the name, or on standard input. There is no flag that takes the token itself, so it never lands in your shell history.

If the connection fails, `add` saves nothing and says why: an unknown host key, a login that wants a password, no Carbon on the server.

## Work on another machine

`--machine <name>` forwards `session`, `draft`, `issue`, `pages`, `secret`, `browser` and `share` commands through this server to a machine from `carbon machine ls`. Put the flag before or after the command:

```bash
carbon --machine vps session new "Run the load test" --title "Load test"
carbon --machine vps session ls
carbon session ls --machine all
carbon session ls --machine all --all --json
carbon session send <session-id> "Use the staging database."
carbon --machine vps pages list
```

`session ls --machine all` lists this machine and every connected machine. `--all` is separate: it includes every project. Other commands require one machine.

A command naming a session id finds its machine automatically if the local server does not hold that session. Page and draft ids do not have this lookup; pass `--machine` when they belong elsewhere.

For sessions and drafts, Carbon finds the other machine's checkout by the repository's `origin` remote. If there is no matching checkout, attach one there or pass `--project <path on that machine>`. A `--base <session-id>` becomes that session's branch, which must also be available on the target machine. Push it first if needed. Pages' project paths always name projects on the owning server.

Connections work in one direction. Adding `vps` here lets this machine reach it; `vps` can message back only if it also adds this machine. Forwarded commands do not hop through another server to a third machine.

## Limits

- `carbon server` installs browser libraries and ffmpeg with apt alone.
- On a Mac, the background server runs only while you are logged in.
- `carbon machine` and `carbon server` change this machine only. Neither takes `--machine`.
- Remote commands need a local server and a working connection to the target. They do not install or update an older target server for you.
