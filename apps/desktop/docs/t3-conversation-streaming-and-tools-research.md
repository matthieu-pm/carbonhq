# Conversation streaming and tools in T3 Code and Carbon

Reviewed November 23, 2026 against [T3 Code main at `b5e1f91c`][t3] and [Carbon main at `40085e25`][carbon]. The adjacent T3 checkout was at `a21d7887` and helped locate the relevant paths. The findings below use the two upstream snapshots.

Start with **live command output**, **recoverable live previews**, and **deterministic replay through the chat UI**. Live command output answers a question users cannot answer from a running row today. Preview recovery fixes a protocol gap that affects remote readers joining a turn mid-stream. Replay gives both changes an inexpensive way to prove their timing and failure behavior.

## How the two pipelines work

| Layer | T3 Code | Carbon |
| --- | --- | --- |
| Provider intake | Per-provider adapters normalize updates into run and turn items. Streamed assistant text and reasoning pass through a response pacing filter. [Run execution][t3-run], [assistant filter][t3-filter] | Harness mappers produce `AgentEvent`s. The common ingest path publishes events and appends durable events to session JSONL. Deltas drive previews. [Ingest][c-ingest], [event persistence][c-persist] |
| Live delivery | The client subscribes to a thread. The stream starts with replay or a bounded projection and coalesces superseded live updates. Command output has a separate per-item subscription. [Thread subscription][t3-ws], [coalescer][t3-coalesce], [output hub][t3-output] | A server connection receives agent events and opens with `live_state`. Committed history catches up via bounded event-ID replay or a replacement tail. The writers already reserve capacity for committed events and can drop previews under load. [Server hub][c-hub], [live state][c-live], [reconnect budgets](reconnect-budgets.md) |
| Rendering | Stable timeline row identities, row-local live text subscriptions, and a virtualized list keep text updates local. Older work can load on disclosure. [Row subscriptions][t3-row], [virtualized list][t3-list], [deferred work][t3-deferred] | A frame-batched external store feeds the preview. The transcript commits the completed item and retires its preview together. Chat mounts recent turns first, then backfills and anchors older content. [Preview store][c-preview], [handoff][c-handoff], [turn window][c-window], [chat backfill][c-scroll] |

Carbon already has partial tool headers, pending and grouped tool rows, inline diff and file-range previews, background task tracking, permission and question cards, and an event-ID recovery path. The earlier [orchestration research](t3-orchestrator-v2-research.md) covers durable task delivery and request receipts. CBN-105 subsequently shipped the reconnect budgets that research proposed. ## Streaming and transport

1. **Restore the open response after reload, reconnect, or a dropped preview.** T3 can hydrate an in-flight item from its current projection, then continue live. Carbon's opening state contains asks, tasks, queued prompts, and secrets. The preview store appends only to an open block, so a client that misses the block start has nowhere to append, and a missing append can leave a hole until the committed event arrives. Keep a bounded server-side preview keyed by session and block identity. Deliver a current snapshot and offsets for later appends, and clear it on commit, stop, or provider exit. Start with assistant text and visible thinking. Tool-input previews only need safe display metadata and a bounded prefix. [T3 thread subscription][t3-ws], [Carbon state][c-live], [Carbon append guard][c-preview], [Carbon preview delivery][c-hub]
2. **Coalesce deltas before WebSocket serialization.** Carbon batches paint, while its hub still serializes and fans out each published delta. T3 coalesces replaceable updates within a short window and preserves meaningful ordering. Merge contiguous appends or send the newest bounded preview from item 1. Flush before any committed boundary that can retire the preview. Record message count, bytes, and time to first visible text before tuning cadence. [T3 coalescer][t3-coalesce], [Carbon hub][c-hub], [Carbon preview store][c-preview]
3. **Send detailed previews where someone is watching.** T3 scopes details to a thread subscription. Carbon broadcasts to all clients on a server, including background session previews. Preserve server-wide lifecycle events, permission requests, and status for sidebar and Crew. Make high-frequency previews opt-in for the selected chat, visible Crew panes, and other active transcript views. Opening a view needs a snapshot before subsequent appends. Profile multiple clients and busy sessions before changing the default wire behavior. [T3 thread subscription][t3-ws], [Carbon hub][c-hub]
4. **Profile the transition from preview to committed history.** Carbon's common ingest publishes ahead of append. The source establishes the order. A reader-visible crash or reconnect race still needs a fault-injected replay. Verify behavior around publish, append, and reconnect, including an append failure. If a client can see a committed row that disappears after recovery, move the durable publish boundary or supply an explicit recovery signal. Include attachments and pending-question ordering in the test. [T3 commit and publication][t3-sink], [Carbon ingest][c-ingest], [Carbon persistence][c-persist]
5. **Add optional pacing for readers who want a calmer transcript.** T3 offers finished paragraphs or finished turns, with an idle flush in paragraph mode. Carbon can keep its current live behavior as the default and offer paragraph pacing as a client preference. Keep tool activity and questions immediate. Handle long paragraphs, unfinished fences, provider text replacements, and a model pausing mid-sentence. [T3 pacing logic][t3-filter], [T3 setting][t3-setting], [Carbon preview rendering][c-preview-ui]
6. **Give iOS live response text.** Carbon's Swift decoder currently treats deltas as ignorable, and its transcript builds from stored events. Use the snapshot and append contract from item 1, scope it to the visible conversation, and reuse the committed transcript as the fallback. Test backgrounding mid-response and rejoining over a slow link. [T3 thread state][t3-detail], [Carbon Swift wire][c-ios-wire], [Carbon Swift transcript][c-ios-view]

## Transcript cost and navigation

7. **Update the active turn without rebuilding settled turns.** T3 caches rows and updates live text in its own row. Carbon already isolates delta renders and memoizes settled turn components, but a new committed event feeds a fresh event array through the transcript builder. Measure a long chat with many short tool events. If projection dominates, reuse settled turn projections and fold the active turn incrementally. Preserve late subagent results, ask decisions, queued prompts, and the consequences of prepending history. [T3 row cache][t3-rows], [Carbon chat derivation][c-chat], [Carbon builder][c-build]
8. **Virtualize the transcript when long histories warrant it.** Carbon's staged backfill reduces opening latency and eventually mounts the entire transcript. T3 keeps a measured visible window. Prototype a turn-level window that keeps row heights, expansion, selection, and focus stable. Profile a single tool-heavy turn too, since it may need a window of its own. Verify anchor preservation on art and image loads, pane resizing, deep links, and reopening the thread. [T3 virtualized list][t3-list], [Carbon turn window][c-window], [Carbon scroll anchoring][c-scroll]
9. **Measure open-block Markdown cost.** Both clients use streaming-aware rendering. T3 also caches settled block parsing and file-link scans, and avoids caching the constantly changing last block. Profile Carbon's Streamdown path with long fences, tables, file links, and prose. Optimize measured repeat work in Carbon's renderer or plugins, with whole-message parsing when syntax requires cross-block context. [T3 Markdown scans][t3-markdown-scan], [T3 block rendering][t3-markdown], [Carbon Markdown][c-markdown]
10. **Restore a reader's position when switching chats.** T3 remembers a row and offset and distinguishes following the end, anchoring a new turn, and reading history. Carbon's Chat resets follow to the end on session changes. Save the visible turn ID and offset for each session and pane when reading history. Keep live-end following for visits that left at the end. Test composer growth, user scroll gestures, and restoration before the target page is mounted. [T3 follow states][t3-follow], [T3 restore][t3-restore], [Carbon chat scroll][c-scroll]
11. **Find text across unloaded history.** T3 searches server-side and resolves results into the timeline. Start Carbon with a bounded per-session search of prompts and assistant replies, returning stable event or turn IDs and snippets. Add older-page navigation and highlight the actual match. Consider an index and cross-session search once the per-thread behavior and latency are established. Carbon's existing turn rail can also show the current viewport and search hits. [T3 find][t3-find], [T3 message index][t3-index], [T3 minimap][t3-minimap], [Carbon paging commands][c-page], [Carbon turn rail][c-rail]
12. **Link to a specific answer or quote.** T3 carries a message identity and selection anchor so a citation can reopen its source. Carbon could start with a turn or event link that opens the appropriate server and session, pages to the source, and highlights it. A reply quoting a passage can build on that same link. Define what happens when a session is forked, edited, deleted, or unavailable. [T3 selection citations][t3-cite], [Carbon event identity][c-event]
13. **Announce meaningful progress to assistive technology.** T3 tracks turn announcements and deduplicates lifecycle speech. Carbon has a polite working indicator. Add a session-scoped announcement for waiting for input, failed or stopped work, and a completed reply, respecting focus on existing request cards. Check VoiceOver during rapid updates and across reconnect. [T3 announcer][t3-announce], [Carbon working indicator][c-working]

## Tool output and activity

14. **Stream output from a running shell command on expansion.** Carbon maps Codex command start and final aggregated output, exit code, and duration. Its parser ignores `item/commandExecution/outputDelta`. T3 keeps a bounded per-item output tail, subscribes when the row opens, and swaps to stored output on completion. Start with Codex and an expandable Carbon command row. Show truncation and preserve scroll if the reader moves away from the end. Use the existing command result as the final authoritative output. Grok is a follow-on because Carbon already captures in-progress output snapshots for the final result. Claude needs separate provider support. [T3 adapter][t3-codex], [T3 output hub][t3-output], [T3 panel][t3-output-ui], [T3 Claude output][t3-claude-output], [Carbon parser][c-codex-parser], [Carbon mapper][c-codex-map], [Carbon Grok output snapshots][c-grok]
15. **Load full tool detail on demand.** T3 projects smaller wire summaries for large results and serves item detail by identity and revision. Carbon archives image bytes separately but publishes tool result payloads, while its row already clips the display preview. Start with large shell and MCP results whose transfer cost is easy to measure. Send tool type, status, exit code, duration, summary, and a detail handle. Fetch raw or richer content when opened, using existing JSONL data for old sessions. Verify that detail loads given a fresh live row and that older clients and historical sessions still read. [T3 wire projection][t3-wire], [T3 inspector][t3-inspect], [Carbon tool payload][c-tool-payload], [Carbon result ingest][c-ingest], [Carbon result preview][c-tool-result]
16. **Defer loading older collapsed tool bodies.** T3 initial thread detail can defer older work and hydrate it on expansion. Build on item 15 by retaining compact per-turn activity and failure summaries even when large bodies have been deferred. Match tool start, result, edit, and task by identity across pages. Test turns that span a paging boundary and a tool completing after the main turn. [T3 subscription options][t3-ws], [T3 deferred work][t3-deferred], [Carbon page and recovery][c-replay], [Carbon transcript builder][c-build]
17. **Show failures and duration in collapsed groups.** Carbon already summarizes pending calls and diff totals, and intentionally reserves failure styling for individual rows. T3 surfaces an aggregate failure signal. Introduce a quiet indicator for actionable failures and retain Carbon's routine-error distinction. Surface command duration or exit status where it helps explain a long wait. Count simultaneous calls and treat failures followed by successful retries deliberately. [T3 group summary][t3-group-failure], [Carbon tool group][c-group], [Carbon error treatment][c-tool]
18. **Keep expanded tool groups usable as they grow.** T3 windows large groups and remembers their position. Carbon mounts grouped calls when opened. Preserve disclosure by stable call identity when a late result changes the group, and cap the rendered cost of groups with hundreds of calls. Check focus, keyboard navigation, copied output, and anchors when rows change height. [T3 group window][t3-group], [Carbon group][c-group]
19. **Add contextual approval history.** T3 relates an in-timeline approval to the action and shows whether the provider can still take a reply. Carbon already renders the command, actual provider options, and separate question cards. Link the live card to its tool row when an identity is available. If past decisions need to be inspectable, persist the outcome and tool reference without replaying a replyable card or exposing the rule payload. [T3 approval row][t3-approval], [Carbon permission card][c-permission], [Carbon persistence rules][c-persist]
20. **Recover an approval whose response fails.** T3 tracks in-flight responses by request ID and surfaces send errors. Carbon locks the card after a click, and the server removes a request from its pending map before writing the reply. Use a scripted transport failure to check when the request is still answerable and when the outcome is uncertain. Show the server's outcome on the card. Offer retry only for a request that the server confirms is still pending and undelivered. [T3 response handling][t3-approval-send], [Carbon card][c-permission], [Carbon reply delivery][c-reply]
21. **Give sibling subagents a compact summary with individual access.** T3 can group adjacent related children and show their live status. Carbon deliberately keeps subagent rows outside generic tool grouping and already opens each child's panel. Consider a dedicated sibling group for large parallel runs, with each child, its status, elapsed time, and existing panel one interaction away. A failed or waiting child should still be easy to find after the parent turn ends. [T3 subagent rows][t3-subagents], [Carbon grouping][c-subgroup], [Carbon subagent row][c-subagent]
22. **Use provider metadata to label MCP tools.** T3 reads tool titles and integration metadata. Carbon already humanizes qualified tool names. Prefer a provider's tool title when available and keep the exact method in the detail. Use an existing Carbon icon as the fallback and keep rows for two servers with the same method name distinct. [T3 MCP tool metadata][t3-mcp-metadata], [Carbon MCP labels][c-mcp-labels]
23. **Support structured MCP results in stages.** T3 has provider-backed MCP App resources and a sandboxed frame. Carbon already reads native MCP resources on its Codex bridge and renders text and images in tool results. First improve human-readable previews for structured results from real tools. Interactive MCP Apps need provider support, resource ownership, capabilities for tool calls, and a sandboxed view. [T3 Claude MCP Apps][t3-mcp], [T3 frame][t3-frame], [Carbon MCP resources][c-mcp], [Carbon tool result][c-tool-result]

## Prompt controls and verification

24. **Edit or reorder held prompts in place.** T3 edits and reorders queue entries through server commands and can promote a queued prompt to steering where supported. Carbon shows queued prompts and cancels the latest. Start with editing an individually identified entry while it is still held by Carbon, preserving text, attachments, and model choices. Make the operation atomic with queue flush and return a clear outcome if the provider already accepted it. Add reorder or steer after validating each harness's capabilities. [T3 reorder][t3-queue], [T3 edit][t3-queue-edit], [T3 steer][t3-queue-steer], [Carbon queued UI][c-queue-ui], [Carbon queue][c-queue]
25. **Make ambiguous sends recoverable.** T3 identifies a submission by a command receipt and derives the message ID from the command ID. Carbon's reconnect can reconcile queued rows with replay. Extend the earlier research on command receipts to the user's send path. Surface a pending state until a retry can resolve the original attempt, and keep the draft and attachments available when acceptance is uncertain. Test a lost successful response and two clients retrying the same submission. [T3 command identity][t3-send], [Carbon resync][c-resync], [Carbon orchestration research](t3-orchestrator-v2-research.md)
26. **Run a scripted conversation through the real chat.** T3's dev replay emits paced provider frames through production adapters and can wait for a permission response. Carbon has normalized event fixtures and headless fake-harness checks. Add a reusable scenario that runs into desktop chat through a scratch server and can also drive the remote client. Include a long answer, tool-argument streaming, live command output, failed calls, a question, a subagent, and reconnect on a deterministic boundary. [T3 replay agent][t3-replay], [Carbon headless fixtures][c-fixtures], [Carbon focused streaming tests][c-stream-tests]
27. **Measure the costs at each boundary.** T3 separates live output state, thread stream pacing, and row rendering. Extend Carbon's reconnect workload with captures for time to first visible text, frames and bytes per viewer, active-turn projection time, scroll stability, and retained tool-result memory. Compare one active chat, many background sessions, a slow reader, and a very long response on identical fixtures. Use observations from those cases to size the work in items 2, 3, and 7–9. [T3 coalescer][t3-coalesce], [T3 row subscription][t3-row], [Carbon reconnect measurements](reconnect-budgets.md)

## Implementation order

| Pass | Deliverable | Acceptance check |
| --- | --- | --- |
| 1 | Scripted real-chat replay and Codex command output | Open a running command late, reconnect, collapse and reopen, then finish with a single final output. Memory stays bounded for a noisy command and a stalled reader. Use the fixture to exercise approval-response failure as well. |
| 2 | Recoverable assistant and thinking previews | Join or reconnect mid-block. Lose or duplicate a preview frame. Receive a commit while recovery is in flight. Text converges and there is one final row. Requests remain actionable and older clients still reconnect. |
| 3 | Smaller tool payloads and retained reading position | Open a long session with large tool results. Load detail by identity, including a pre-change session. Switch away while reading history and return to the same turn. |
| 4 | Find in chat, queue editing, and activity improvements | Find a match on an unloaded page. Edit a held entry as the provider is about to receive it. Confirm the group, approval, and subagent summaries stay consistent through late results. |
| After profiling | Preview subscription scoping, incremental projection, virtualization, and Markdown tuning | Compare transport bytes, main-thread work, and scroll behavior against the replay baseline. Verify keyboard focus, iOS compatibility, and recovery with multiple clients. |

This was a source review. Four existing Carbon Vitest files covering streaming, transcript projection, the turn window, and resync passed all 83 tests. Those eight source and test files were byte-identical in the local checkout and the reviewed Carbon revision. Neither app UI was exercised, and the proposed failure cases and performance gains remain to be measured.
